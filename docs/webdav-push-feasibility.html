Supporting WebDAV-Push

Feasibility assessment and implementation scope for ContactzillaSync

Android client: com.atomicasoftware.contactzillasync  ·  Server: dav.contactzilla.app (SabreDAV)  ·  9 September 2026

Why this matters

Contacts currently reach the device by polling. Android's WorkManager enforces a fifteen-minute floor on periodic work, so fifteen minutes is the fastest the app can ever poll — a limit the codebase already acknowledges in SyncWorkerManager.effectivePeriodicInterval(), which silently raises any shorter interval to the minimum. Server-side changes therefore take up to fifteen minutes to appear, and no amount of client work will improve that.

WebDAV-Push removes the constraint entirely. The server notifies the device the moment a collection changes and the client syncs within seconds, while also using less battery than polling because the device stops waking up to ask about changes that haven't happened. It is the only route to near-instant contact updates.

Current server status

A PROPFIND against /addressbooks/kindsapphireevolve/clients/ for transports and topic in the https://bitfire.at/webdav-push namespace returns 404 Not Found for both properties. The server advertises no push support today, so the client correctly falls back to polling.

The transport decision

Web Push needs something to carry the message to the handset, and this is the one genuine product decision in the project. It should be settled before any client work starts, because it determines what the app is.

OptionTrade-off
UnifiedPush distributor
org.unifiedpush.android:connector		 Fully open, no Google dependency, and what DAVx⁵ ships. But it requires users to install a separate distributor app such as ntfy and connect it manually. Fine for hobbyists; a non-starter for MDM-managed business users who will not install a second app.
Embedded FCM distributor
org.unifiedpush.android:embedded-fcm-distributor		 No second app — push works out of the box. Was already a dependency before the removal. Requires a Firebase project, google-services.json and a hard dependency on Google Play Services. The build currently has a single ose flavour and no Firebase anywhere, so this changes the nature of the app.
Both, by flavour Keep ose pure with the plain connector and add a Play-targeted flavour with the embedded distributor. Most flexible, most build complexity, and requires maintaining two release artefacts.

The decision can be deferred during development: build and test against ntfy first, then decide on FCM before shipping to end users.

The server is the larger piece of work

There is no ready-made sabre/dav plugin for WebDAV-Push. The only reference server implementation is bitfire's Nextcloud extension, nc_ext_dav_push. This means writing a Sabre\DAV\ServerPlugin against the specification draft, registering it with Server::addPlugin(). It must do five things.

1. Advertise capability

Expose transports, topic and supported-triggers through propFind on address book collections. The transports element carries the server's VAPID public key. The specification requires that topic and supported-triggers are not returned for resources that don't support push.

2. Accept subscriptions

Handle POST with Content-Type: application/xml and a push-register root element. Persist the subscription against the authenticated user and respond 201 with Location and Expires headers. Re-registering an existing identifier must update the record rather than create a duplicate.

3. Support unsubscribe and expiry

Handle DELETE on the registration URL, and sweep expired subscriptions. The Expires value the server returns may be shorter than the client requested.

4. Deliver push messages

On a collection change, send a VAPID-signed, encrypted Web Push message to the stored endpoint, carrying a push-message XML body with the collection topic and ideally the new sync-token. Two practical notes: delivery must happen out of band from the request that caused the change, so a queue and worker are needed rather than inline sending; and the encryption (RFC 8291 and 8292) is fiddly enough that minishlink/web-push is strongly preferable to a hand-rolled implementation.

5. Honour Push-Dont-Notify

The client already sends this header on its own writes. If the server ignores it, every change the app makes will push a notification back to the device that made it, causing a redundant sync loop. Registration URLs must be matched in the exact form the server originally issued in the Location header.

Suggested sequencing

  1. Build the sabre/dav plugin first. The client is useless without it, and it can be validated independently against DAVx⁵, which already implements the protocol. This de-risks the server work before any Android effort is spent.
  2. Port the client push/ package. Re-add the UnifiedPush connector, the manifest service entry, and the five deleted classes under the current package name; re-wire the hooks in RefreshCollectionsWorker, BaseSyncWorker and CollectionSelectedUseCase; and make fromPush do something again.
  3. Test with ntfy as the distributor, end to end.
  4. Settle the transport question and, if going the FCM route, add Firebase and restore the distributor settings UI.
  5. Reconsider the poll interval. Once push is live, the fifteen-minute default becomes a fallback for devices without a working distributor and could be relaxed to reduce battery use.
